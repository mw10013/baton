### 1.4 Risks

- **Reconcile inside the order transaction.** `afterWrite` runs on `syncTransaction`'s sync scheduler with the input gate closed. Reconcile must only read and write SQLite there: `listActiveWorkflowsByTags` is plain statements; the D1 teams are read before (`eligibleContext`); `countOrder`, if ported, is storage only. A D1 or network call inside would stall the actor. The plan pins the order with a unit test.
- **Reconcile all's cost.** One transaction per open paid order, bounded by retention (365 days) and `maxOpenOrders` (2,500). A Turn on on a full shop walks every open order; within the DO's CPU limit but worth a log line with counts and time (legacy logs counts).
- **Interleaving.** A procedure's D1 read opens the input gate; a webhook's reconcile and a Turn on's reconcile all may interleave. Each pass is idempotent and reads stored rows, so every order ends under the newer snapshot (legacy pass rule 3's reasoning).
- **The run creation path counts the order for billing** in legacy (Q3). Leaving it out now means G has to count orders that already have runs, or a reset.
- **Size.** About 9,500 legacy lines and ~200 test titles; the largest slice yet. e2e grows by ~60 titles (16 orders, 2 home, 40 workflows list and page, 5 member area).
- **e2e and real Shopify.** Fixture orders are not in Shopify: the order page's Sync from Shopify and View in Shopify are dead for them (the orders index already hides both for fixture orders). Specs that need a real order use `scripts/test-order.ts` on the e2e store, as `orders.spec.ts` does.

## 5. Questions and recommendations

1. **Where does it run?** `wt-01` holds the user's e2e flakiness thread; F touches the contract, the actor, the client and both route trees, so its halves do not split cleanly across checkouts. **Recommendation:** one implementation thread on `main`, sub-slices in order, with a `CHECKPOINT` after sub-slice 4 (the Backend half) so the orchestrator can review before the screens.

2. **Names.** Roadmap §0.2 named `makeRunRepository` and `makeRuns`. **Recommendation:** `makeRunRepository(sql, transaction)` in `shop-actor/run-repository.ts` with legacy's method and error names; `makeRuns({ runRepository, orderRepository, workflowRepository, membershipRepository, notify, shop })` in `shop-actor/runs.ts`, holding legacy `ShopWorkAgent`'s run half: `reconcileAll(caller, id)` (legacy `reconcileAllNow`), `reconciler()`, `eligibleContext()`, one method per run procedure, the reads. Its log operation prefix is `Runs.` (legacy `ShopAgent.`). Order-page and orders-index reads belong to orders, not runs, by area, but they read runs and the D1 teams the way runs does; they go on `makeRuns` too, as legacy's `ShopWorkAgent` held them, so `makeOrders` stays the Shopify sync. Legacy's `currentWhere.ts` becomes a private of the run repository.

3. **The billing half of creating a run.** Legacy's `insertRun` counts the order inside the transaction (`countOrder`: `countedAt`, the cycle, `ordersThisCycle`, a `UsageEvent`), and five run paths flush the usage queue after. Billing is G (roadmap Q7). **Recommendation:** seams, as E's `reconcileAll`: `makeRunRepository` takes `countOrder: (orderId, now) => Effect<void, SqlError>` and `makeRuns` takes `flushUsage: Effect<void>`, the actor passing no-ops; the call sites are legacy's (`insertRun` after the insert; `ensuring` after reconcile all and Attach; after the webhook, Sync from Shopify and the stream) and a unit test records them. The five metering titles and `ShopUsage`'s triggers table go to G. Orders that get runs before G stay uncounted; G arrives with a reset (cloud reset policy) or backfills `countedAt` from `Run`. The alternative, porting `countOrder` and the cycle now, pulls billing's domain into F.

4. **Notice keys.** Legacy's `publish` was one keyless invalidation every live screen re-read on. Here a notice names keys. Everything F reads live (the orders index, the home page's strip, the order page, the workflows list, the member's workflow page) changes on the same writes: an order write, a reconcile, a run verb, a definition change. **Recommendation:** one key, `ORDERS_KEY`, for orders and their runs, read by all five screens; every run write notifies it on its success variant, the webhook also when a run moved. E's sites stay. Its JSDoc becomes "an order or one of its runs changed". The alternative, a `RUNS_KEY` that every order and definition site also sends, adds a second name for the same set of writes.

5. **The list memos.** Legacy memoized `listOrders` (per input) and the workflows list's open rows (per team set) in the object's memory, cleared by every `publish`, so N sockets re-reading after one write cost one read (legacy `list-memo.test.ts`). **Recommendation:** port both as Effect `Cache`s built per activation, cleared by `notify` when it names `ORDERS_KEY`; a hibernated actor starts empty, which is correct. Its titles go to unit.

6. **The orders read.** Slice A's `MerchantListOrders` and `listOrders` loader take `OrdersListInput { limit, cursor }` and answer `OrdersListPage` ("without its runs, counts and matches"). **Recommendation:** replace both with the domain's `ListOrdersInput` and `OrdersIndexData` and legacy's `listOrders` SQL with its twins; delete the contract's `OrdersListInput` and `OrdersListPage`. The index's interim per-row Sync column goes (legacy has Sync from Shopify on the order page); `from-shopify` redirects to the order page by the legacy id, as legacy and its JSDoc say.

7. **Procedure names for reads.** Legacy's reads kept bare names (`getOrderDetail`, `liveRuns`, `liveRun`) and only writes carried the role; here every procedure is role-prefixed (glossary, Caller). **Recommendation:** `MerchantGetOrderDetail`, `MemberListRuns`, `MemberGetRun`; the stub methods keep legacy's loader names (`getOrderDetail`, `listRuns`, `getRunPage`); writes keep legacy's verbs (`MerchantMarkTaskDone`, `MemberStartTask`, …). Test titles stay byte for byte, legacy names included.

8. **Member routes.** Roadmap Q14 kept `$key` and "legacy's structure under it", but wrote it as `/shop/$key` → the list and `/shop/$key/runs/$runId`. Legacy's structure is `/shop/$shop/` redirecting to `/shop/$shop/workflows`, and `/shop/$shop/workflows/$runId`; its rule is that a screen is never named with "run" and route segments speak the screen word (the workflows list, the member's workflow page). **Recommendation:** legacy's structure verbatim under `$key`: `/shop/$key/` redirects to `/shop/$key/workflows` keeping the search, and `/shop/$key/workflows/$runId`. This amends Q14 (a dated amendment in the roadmap). The roadmap's "work list" and "item page" become the Screens table's names.

9. **Member reads' authorization.** Legacy's member loaders ran `requireMember` in the Worker (D1 membership, then the plan) and passed `teamIds` to the object. Here `ShopAccess.resolve` is the gate and already answers the member's `teamIds`. **Recommendation:** each member loader method (`workflowsList`, `memberWorkflowPage`) resolves the caller through `ShopAccess` and passes `{ teamIds, memberEmail }` to the stub; a non-member gets the layout's not-found ("You no longer have access to this store."); the layout's loader becomes the gate alone (the count snapshot goes, Q10). The plan half of `requireMember` (lapsed) is G.

10. **The counter page.** `/shop/$key` today is the count demo (`MemberGetCount`, `MemberIncrement`, `MemberActivation`, `MemberWhoAmI`; `MerchantGetCount`, `MerchantResetCount`, `MerchantWhoAmI`; `COUNT_KEY`; `ShopPage`; the snapshot's count). Its socket tests (sign-out across windows, removal, displacement, a notice across windows) are real behaviour. **Recommendation:** retire the counter entirely in F; the socket tests re-anchor on the workflows list (a Done in one window shows in another; removal, sign-out and displacement unchanged). Keep `Activation` and `…WhoAmI` only if an integ socket-fact test still needs them; otherwise they go too.

11. **The fixture and progress.** Legacy's seed upserted each order with reconcile, attached the item's chosen `workflow`, applied each item's progress (`done`, `advance`, `started`, `blocked`, `byMerchant`, `by`, `note`), then the order's `after` with a second reconcile, then a reconcile all; seeded orders were marked counted. The fixture here carries the same fields unapplied. **Recommendation:** `loadFixture` and `addFixture` apply them through `makeRuns` and the run repository, in legacy's order, with fixture orders already counted (`countedAt` 0); one notice at the end. Legacy's seed titles that still apply ("seedOrders runs each item on its own progress and leaves its siblings alone", "seedOrders chooses a workflow for an item two claim, and the order stops asking", "seedOrders applies `after` once the work has started, so a cancel closes the run and a quantity change resizes it", "a seeded run records its `by` member as the starter and the doer", "a seeded Done on a team `by` is not on is recorded as that team's first member", "a seeded run's note is written after its progress") move to the fixture's tests with their titles. This is what the member e2e specs arrange through.

12. **The member bar and landing.** Legacy's bar, on each `/shop/$shop/*` page, named the shop and linked its mark to the workflows list, with Help, the email and Sign out; a one-shop member landed on their workflows list after sign-in. Here one bar in the `/shop` layout says "Baton" and links `/shop`; every member lands on `/shop`. **Recommendation:** on `/shop/$key` pages the bar names the shop and its home is the workflows list at the first page (legacy's "the bar's mark opens the list at the first page"); Help waits for I; a one-shop member lands on their workflows list (`homeFor` learns the member's shops). Your stores keeps today's bar.

13. **How much of the home page?** **Recommendation:** the Orders strip only (the index's arrival read, live, seeded from the home loader), above today's links; the plan tiles, Manage plan and `QuotaBanners` are G.

14. **Where legacy's tests land.** **Recommendation:** repository and data-model titles → unit over `ActorSqliteTest`; the matrices' rows → unit, one `it` per row with legacy's rendered title, the cells written as data in the test (roadmap Q4: no source parser); the `callables:` half and every socket title → integ over forged sockets; query-plan titles by `explain query plan` in unit; rows-read titles dropped (Durable Object cursor counters only); e2e titles stay e2e, except those that assert only a part's rendering, which may move to browser tests under the same title (the plan lists which).

15. **Screen parts and helpers.** **Recommendation:** port on demand with legacy's names and `Screen.ts` rows: `Strip` (filter and link cells), `SelectRow`, `StepList` with `FramedList`, `Clamp`, `ClampedProse`, `ResourceRow` (with `RowLine`), `ShowMore`, `Name`, `PageBody`; `LocalDateTime` gains `date`, `time` and `relative`; `useResourceLinkTarget`; the print CSS for the member's workflow page; `/dev/kit` gains their sections. `MeterTile` and `Tiles` wait for G.

16. **e2e on the shared store.** The member specs are serial in legacy (one seeded shop). Here e2e is parallel and each spec adds its own data (`AddToFixture`, `ownMember`). **Recommendation:** each member spec adds its own team, members, workflow and orders under names from its test id and asserts only on them; the order specs likewise (`orders.spec.ts`'s real-order titles through `scripts/test-order.ts`). A spec that needs two members on one team uses two `ownMember`s. No spec loads the fixture.
