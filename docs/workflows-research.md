### 1.1 What legacy does

**Storage** (`WorkflowRepository.ts`, the object's SQLite). One row per workflow; its tasks are one JSON document decoded through `WorkflowTasks` on every read and write, which refuses a list that breaks the step rule (dense from 1, non-decreasing along position) or the task cap. The draft is a second document, `null` until the first edit.

| Method                                                                        | Does                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `listWorkflows`                                                               | Keyset page by name (`limit + 1`), `stepCount` by `json_each`, search by prefix patterns on the name (`prefixPatterns`), state filter (ignored while searching), `matches` when searching; `unassigned` and `emptyTeam` derived per row against the live teams, never stored. |
| `getWorkflow`                                                                 | The row with tasks and draft tasks, or none.                                                                                                                                                                                                                                  |
| `listActiveWorkflowsByTags`                                                   | Reconcile's read: active workflows whose tag is one of the order's product tags, a probe of the unique index (`ACTIVE_WORKFLOWS_BY_TAGS`, pinned by a query-plan test).                                                                                                       |
| `listActiveWorkflowNames`                                                     | The order page's Workflow select options.                                                                                                                                                                                                                                     |
| `workflowSetupFacts`                                                          | `exists` active workflow, `exists` run, one statement.                                                                                                                                                                                                                        |
| `createWorkflow`                                                              | Ceiling (`maxWorkflows` 200), then name, then tag checked (each a typed refusal naming its field; the tag one names the holder), then insert inactive, no tasks, no draft.                                                                                                    |
| `duplicateWorkflow`                                                           | The same checks, the source's tasks under new ids, inactive, no draft.                                                                                                                                                                                                        |
| `updateWorkflow`                                                              | Rename, immediate (runs snapshot the name).                                                                                                                                                                                                                                   |
| `updateWorkflowTag`                                                           | Retag, immediate, never drafted.                                                                                                                                                                                                                                              |
| `setWorkflowState`                                                            | Active needs at least one task and every task on a live team (`NoTasksError`, `TaskUnassignedError`); an empty team does not refuse. Inactive touches nothing else. Never reads the draft.                                                                                    |
| `createDraft`                                                                 | Copies tasks to the draft, idempotent. No screen calls it.                                                                                                                                                                                                                    |
| `applyDraft`                                                                  | One statement: `tasks = draftTasks, draftTasks = null`. Refuses no draft, an empty draft, an unassigned task. Leaves `state`.                                                                                                                                                 |
| `applyAndTurnOn`                                                              | Apply (when there is a draft) and active, one transaction: the editor's Turn on for a never-applied workflow.                                                                                                                                                                 |
| `discardDraft`                                                                | Clears the draft; `NoDraftError` without one.                                                                                                                                                                                                                                 |
| `addStep`, `addTask`                                                          | A new task in a new last step, or after a step's last task; `WorkflowLimitError` past 20 tasks; `StepNotFoundError`.                                                                                                                                                          |
| `updateTask`, `moveTask`, `separateTask`, `joinTask`, `removeTask`, `getTask` | Task-id writes on the draft through `editDraft`: the first write copies `tasks` into `draftTasks` ids included, so the id the editor holds names the same task in both. Edges are no-ops.                                                                                     |
| `deleteWorkflow`                                                              | The definition only; runs survive (they snapshot).                                                                                                                                                                                                                            |
| `unassignTeam`, `teamIdsInUse`                                                | Team delete's half: null `teamId` on every workflow task, draft task and run task pointing at a team, one transaction; every team id in use, for the repair.                                                                                                                  |
| `replaceWorkflows`                                                            | The dev seed: replaces every workflow and run, validating the fixture.                                                                                                                                                                                                        |

Errors are `Schema.TaggedError`s; `agent/ShopWork.ts` maps each expected one to a variant of the callable's result union (`WorkflowResult`, `ApplyResult`, `DiscardResult`, `DraftResult`, `SwitchResult`, `TaskResult`, `DeleteWorkflowResult`), because the object's `runEffect` seam collapsed every failure to a string. Faults (`SqlError`, decode) throw.

**Layout** (`WorkflowLayout.ts`): pure arithmetic over `{ id, position, step }`. `move` slides a task past the neighbouring boundary into a step of its own; `join` merges into the previous step, last among its members; `separate` splits off into its own following step; `remove` closes both gaps; `stepsOf` groups for rendering.

**The agent's checks** (`agent/ShopWork.ts`). `addStep`, `addTask` and `updateTask` check the team against D1's live teams first (`TeamNotFound` as a result); the repository's eligibility checks take the live teams as an argument, read before the transaction. Every write logs one line.

**Screens.**

- **Workflows** (`/app/workflows`): a layout with `state`, `q`, `after` in the URL, kept across the child pages (`retainSearchParamsUnder`); the index pages 50 by name with All / Active / Inactive press-buttons, a search by name, badges (Active, Inactive, No steps, Needs a team, Team has no members), columns Workflow, Status, Tag, Steps, Updated; a Create workflow modal (Name, Tag mirroring `suggestedTag(name)` until edited, `TAG_HELP`), whose `NameTaken` and `TagTaken` land under their fields; on create, the editor opens in a window.
- **Workflow** (`/app/workflows/$workflowId`): the tasks in force (never the draft) as a step flow under a trigger card ("Starts when an order contains a product tagged “x”." and Edit tag); badges; `Last updated on`; `TeamFaultBanners`; Edit (opens the editor window); More actions: Rename, Duplicate (lands in the editor page), Delete ("Items already on it keep going. This can't be undone."); the switch (`WorkflowSwitch`) with its Turn on and Turn off modals.
- **Editor** (`/app/workflows/$workflowId/edit`, in a window or as a page): the draft (or the tasks) as a selectable step flow; an aside to edit the selected task (Name, Team, Instructions with the 500 limit, Move earlier, Move later, Move to its own step, Join the previous step, Delete, Save); Add step and Add task forms; "Create a team before adding steps." with no teams; Apply changes (confirm only when active), Discard changes, Turn on (apply and turn on when never applied), Rename, Delete. Every control writes at once; there is no leave guard; another tab's change re-seeds the aside during render.
- **The editor window** (`workflowEditorWindow.ts`): Flow-style full-screen chrome. The window is a sibling iframe; it reports `applied` and `deleted` over a same-origin `BroadcastChannel`, and modals inside it are hidden through the element (`polarisModal.hideModal`), because `shopify.modal.hide` cannot see them.
- **App Home** (`app.index.tsx`): `SetupGuide` "Getting started", "n of 3 done": "Create a team and add a member" (Teams), "Create a workflow and turn it on" (Workflows), "An item gets a workflow" ("New orders arrive as they are placed."); shown while any fact is false. The same page carries the Orders strip (live `listOrders`), the plan tiles and Manage plan (G).
- **`/dev/kit`**: every part with worst-case data, local only.

### 1.3 What must change for Alchemy and Effect

1. **The actor gains a workflow repository** (Q3): `makeWorkflowRepository(sql, transaction)` in `src/backend/shop-actor/workflow-repository.ts`, beside `makeOrderRepository`, over the activation's SQL client and `syncTransaction`. Legacy's `sql.withTransaction` becomes the `transaction` argument; nested transactions are refused here as in legacy, so the application service calls the repository outside one.
2. **Live teams from `MembershipRepository`.** Legacy's `teams()` read `Repository.listTeams` over `env.D1` inside the object. The actor already yields the D1 membership repository; it gains `listTeams({ shop })` (every team with `memberCount`, at most `maxTeams` rows). A D1 call is outside I/O, so it must run **before** any `transaction(…)`: a storage transaction holds the input gate and its body runs on `syncTransaction`'s sync scheduler, and awaiting a binding inside it is untested here and unneeded. Legacy read teams before the repository call for its own reason (D1 cannot join a DO transaction); the order is kept.

### 1.4 Risks

- **`s-app-window` in this repo.** Untested here: whether App Bridge loads the window's `src` with the guards' search, whether the window's frame gets a session token, and whether `BroadcastChannel` reaches the opener across the admin's iframes. Verify on the dev store before building on it (Q11).
- **D1 inside a transaction.** A `MembershipRepository` call inside `transaction(…)` is untested and may stall the actor. Every handler reads teams first; the plan's rule and a unit test pin the order.
- **Interleaving.** A procedure's D1 read opens the input gate; a second press or a team delete can run between the team check and the repository write. Legacy had the same window and closed it by the team-delete order (D1 first, then null; the next delete repairs); kept.
- **Legacy's integration tests ran on DO SQLite.** The repository tests move to unit over `@effect/sql-sqlite-node` (the orders repository's layer); `node:sqlite` runs only the first statement of a multi-statement call, and `json_each` with `json_extract` must behave as on the DO. The first step proves three of them.
- **e2e and the window.** Legacy's specs drove the editor inside the window's frame (`editorFrame`); Playwright must reach the sibling iframe the admin creates.

## 5. Questions and recommendations

1. **Where does it run?** Nothing else is in flight. **Recommendation:** one implementation thread on `main`; `wt-01` stays idle.
2. **Where do the handlers live?** Legacy has one `ShopWorkAgent` for workflows, runs and orders. This repo split `OrdersAgent` and `MembersAgent`. Recommendation (as written): `makeWorkflowsAgent({ … })` in `src/backend/shop-actor/workflows-agent.ts`. **Decision (review, 2026-10-18):** the structure stays (one actor; one module per area, as legacy's object map) and the naming is fixed from first principles, before E builds on it. "Agent" came from the Cloudflare Agents SDK legacy's object extended and names nothing here. Three roles, one pattern each:

   | Role       | What it is                                                                                                                                                          | Pattern              |
   | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
   | Storage    | One store's SQL for one area, no other logic: a **repository**                                                                                                      | `<Area>Repository`   |
   | Operations | The shop's use cases for one area: check rules across stores, call the repository, follow up (close sockets, reconcile, notify), answer: an **application service** | the area's bare name |
   | Transport  | A procedure **handler**, a **schemaless method**, a **server function**                                                                                             | the glossary's       |

   The **areas** of shop work are orders, membership (members, teams, who is on which team), workflows and runs. Services that front something outside (`Shopify`, `ShopifyAdmin`, `ShopAccess`, `ShopActors`, `Auth`, `Mailer`, `Webhooks`, `Fixtures`) keep their names. The renames, done first in E as a step of its own with no behaviour change:

   | Today                                                                                                             | Becomes                                                                               |
   | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
   | `Members` (`src/backend/members.ts`)                                                                              | `MembershipRepository` (`membership-repository.ts`)                                   |
   | `ShopSessions` (`shop-sessions.ts`)                                                                               | `ShopSessionRepository` (`shop-session-repository.ts`)                                |
   | `OrdersBulkRepository` (`orders-bulk.ts`): stores nothing, it submits, finds and cancels a Shopify bulk operation | `OrdersBulkOperation` (`orders-bulk-operation.ts`)                                    |
   | `makeOrderRepository` (`shop-actor/orders.ts`)                                                                    | the same, in `shop-actor/order-repository.ts`                                         |
   | `makeOrdersAgent` (`shop-actor/orders-agent.ts`)                                                                  | `makeOrders` (`shop-actor/orders.ts`)                                                 |
   | `makeMembersAgent` (`shop-actor/members-agent.ts`)                                                                | `makeMembership` (`shop-actor/membership.ts`)                                         |
   | (new in E)                                                                                                        | `makeWorkflowRepository` (`workflow-repository.ts`), `makeWorkflows` (`workflows.ts`) |
   | (new in F)                                                                                                        | `makeRunRepository`, `makeRuns`                                                       |

   "Workflow" alone is always the product's definition; Cloudflare's is always the **orders sync Workflow** (`OrdersSyncWorkflow`), and the `workflows` parameter that carries its handle into the orders application service becomes `ordersSync`. Tests move and rename with their modules. The glossary gains **Repository**, **Application service**, **Area** and the workflow rule, and its **Handler** entry says how a handler differs from an application service. The roadmap records it as an amendment (§0.2).

3. **Port the whole repository, or only what E's screens call?** **Recommendation:** the whole of `WorkflowRepository` but `replaceWorkflows`, with legacy's method names: `listActiveWorkflowsByTags` (with its query-plan test) and `listActiveWorkflowNames` are the repository's surface and F needs them; `createDraft` keeps its test. `replaceWorkflows` and `seedWorkflows` are not ported: the fixture (`insertFixtureRows`, `FixtureWorkflow`'s checks) already does their job.
4. **Where does `WorkflowLayout` go?** Legacy keeps it in `src/lib/`, outside the domain, and the domain's JSDoc names it (`WorkflowLayout.move`). Roadmap Q3 fixed four context files. **Recommendation:** `src/domain/workflow-layout.ts`, imported as `import * as WorkflowLayout`, inside the shop-work context for the import-direction lint (it imports `shop-work.ts`'s types and nothing else). The repository and `WorkflowSteps` (`stepsOf`) both use it, so it cannot live in the backend. This is a fifth file in `src/domain/`, which Q3 did not foresee; the alternative is a section of `shop-work.ts`, which is already 4,100 lines.
5. **Result unions as data, or typed errors?** Legacy answers each workflow write with a tagged union as data (`WorkflowResult`, `ApplyResult`, …), because its seam lost error types; slice C declared typed errors (`TeamNameTakenError`) on its procedures but kept `DeleteTeamResult` as data. The unions are already ported in `shop-work.ts`, and the screens switch on `_tag`. **Recommendation:** keep legacy's unions as each procedure's success; no declared error. Faults stay defects (the lost-socket and defect copy is `thrownCopy`, as on every page).
6. **Reconcile with no runs.** Legacy reconciles after Apply and Edit tag (when active) and after the switch, Turn on, delete and team delete (always). **Recommendation:** a `reconcileAll(caller, workflowId)` argument on `Workflows` and `Membership`, with legacy's `reconcileAllIfActive` rule in the application service; the actor passes a no-op until F fills it. Unit tests record the calls, so the sites are pinned now and F only supplies the body.
7. **Notices.** Legacy publishes after Edit tag, Apply, the switch, Turn on and delete (on success) and after team delete (always), because the order page's Workflow select reads them. No screen reads workflows live in E, and every workflow page refreshes by `router.invalidate` after its own write, as legacy's did. **Recommendation:** port the sites now as `notify([ORDERS_KEY])`, the key the order screens read and F's order page will join; pinned in integ by legacy's two titles ("Edit tag and Apply publish to every screen whether or not a run moved; a refused call publishes nothing"; "turning a workflow on or off, deleting it, or deleting a team publishes to every screen; a refused call publishes nothing"). No workflows key, and no teams key: the editor's team select is loader data, refreshed after every task write, as legacy's.
8. **The team-delete pointer half.** **Recommendation:** inside `Membership.deleteTeam`, after the D1 delete and before the closes, as legacy and slice C's seam say: `teamIdsInUse`, then `MembershipRepository.listTeams` (ids in use read first, legacy's reason), then `unassignTeam` for this team and each in-use id gone from D1, then the reconcile seam, then `notify([ORDERS_KEY])` on both answers. `Membership` gains `workflows` (the repository), `reconcileAll` and `notify`. `NotFound` still nulls, as legacy.
9. **The setup guide's read.** Legacy's home loader read D1 and the object in one `Effect.all`. **Recommendation:** `BackendApi.setupFacts`: the session-token and `ShopSession` checks, then `MembershipRepository.teamWithMemberExists` and `ShopActors.workflowSetupFacts` together; the stub method reads the actor's two `exists`. The `run` fact reads `Run`, false until F creates runs; the step shows "Not done" until then, which is true.
10. **`removeWorkflow` and `getWorkflowDetail`: keep legacy's callable names?** Legacy named them around the agents SDK's own `deleteWorkflow` and `getWorkflow`, a collision that does not exist here; the repository was already `deleteWorkflow` and `getWorkflow`. **Recommendation:** `MerchantDeleteWorkflow` and `Workflows.deleteWorkflow`; the stub read keeps `getWorkflowDetail` (it returns `WorkflowPageData`, more than the repository's `getWorkflow`). Test titles stay byte for byte, "removeWorkflow" included.
11. **The editor in an `s-app-window`.** Legacy opens the editor in App Bridge's full-screen window after Create and on Edit, with a `BroadcastChannel` back to the opener and element-based modal hiding; the route also works as a page (Duplicate lands there; `?chrome=window` only changes chrome). **Recommendation:** port both. The editor lands first as a page; then, after a check on the dev store (the window loads with the guards' search and a session token, and `applied` reaches the opener), the window, `workflowEditorWindow.ts` and `hideModal` through the element. If the check fails, Edit and Create navigate to the editor page instead, recorded in the plan, and the window is a follow-up.
12. **Screen parts.** **Recommendation:** port on demand (roadmap Q11) the parts these screens use and this repo lacks, with legacy's names and their `Screen.ts` rows: `Fields`, `PageNote`, `Panel`, `EmptyAside`, `FootLine`, `Connector`, `Prose` (with its `.prose` CSS), `SelectableCard`; for the home, `SetupGuide`. Helpers with them: `workflowShared.ts`'s copy and functions, `retainSearchParamsUnder` in `-search-params.ts`, `DELETED_TOAST.workflow`. `Strip`, `Tiles`, `MeterTile` wait for the home's orders strip and plan (F, G).
13. **How much of App Home?** Slice C's Q15 brought the guide here. **Recommendation:** the setup guide only, with legacy's three steps, copy and "n of 3 done"; the page keeps its links below it until the strip and tiles arrive. No live read.
14. **`/dev/kit`.** Roadmap Q11 brings it with E. Legacy's is local-only and shows every part with worst-case data. **Recommendation:** port it with the parts that exist after E (the index, editor, guide and text-limit sections; worst-case names, tags, a 20-task step), gated as `/api/dev` is: not found where the stage binds no `DEV_ENDPOINT`, so never on staging. Each later slice adds its parts' sections. A browser test renders it once, as a smoke test for every part.
15. **The workflows index page size.** Legacy's index pages 50 (`WORKFLOWS_PAGE_SIZE`), against the controls table's 25 for an index. **Recommendation:** 50, as legacy; the 200-workflow ceiling makes four pages.
