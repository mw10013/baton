Diagnosis

Seven things making the page hard to read

Most of these are one fault wearing different clothes: the page shows every fact at the same weight, so nothing reads as the answer.

01 “Signet ring started for 1 item” It restates the card below it, above the card, in the quietest type on the page. Cut it. On a multi-item order the same information is a count in the header, not a paragraph.
02 A “Line items” card wrapping one line item Two headings for one thing, and the outer one is schema vocabulary. Drop the wrapper. Each item is its own card, titled with the product.
03 “Workflow” vs “Order workflow” Identical cards for two different ideas, told apart only by a heading. Name them by when they happen — making the item, then shipping the order — or fuse them into one pipeline (B).
04 Free text inside a badge A badge is for a closed vocabulary: active, pending. A merchant's block reason is a sentence and will someday be a paragraph. Give it a strip that wraps, clamps at two lines, and carries its own Unblock.
05 Manage unfolds a form per step Three bordered boxes, three team pickers, a block field and a Cancel — inside the card you were reading. One action inline (the step that's actually ready), everything else behind an overflow menu or a drawer.
06 “Attach workflow” always on screen A rare, deliberate act rendered as a permanent empty select on every item, every visit. Make it a link that reveals the picker, or move it into the overflow menu.
07 Nothing says what to do next Stage, trail, status, flag, actor, time — all present, none promoted. Promote the live step. One line that names the step, its team, and its one button.

On quantity in Order details

Your instinct to back off was right. Quantity is a property of a line item, not the order — it already sits on the item card as ×1, and copying it into the aside means two numbers to keep in agreement. What the aside is missing is the shape of the order, which is a genuine order-level fact and only interesting above one: Items · 3 items, 7 units. Show that row only when there's more than one item.

A

Quiet by default

The smallest change that fixes the noise. Same information architecture, but everything not being acted on right now recedes: one card per item, one live step with one button, everything else in an overflow menu. Shipped as an edit to the page you have.

B

One pipeline: make, then ship

Kills the “two kinds of workflow card” problem by denying the premise. An order isn't item workflows plus an order workflow — it's one run of work with a making phase and a shipping phase, and the second starts when the first finishes. That sentence is the layout.

C

The step table

Stops pretending cards scale. Every step of every run on the order becomes one row with the same five columns, so a 1-item order and a 9-item order read identically and attention is a stripe down the left edge. The densest option, and the only one that survives a big order.

Fits when

  • The merchant is a production manager, not the maker.
D

Glance, then drawer

Splits the page's two jobs apart instead of stacking them. The page is read-only status you can take in from across the room; every intervention opens a drawer with room to breathe. Nothing expands in place, so the page never changes shape under you.

Keeps

  • Editing gets real room — notes, reasons and team pickers stop being cramped.
  • Status is legible at a glance: meter, one line of context, one badge.

Costs

  • Every action costs an extra click, including the common “mark this done”.
  • A drawer needs its own live-update handling when a webhook lands while it's open.
  • Two surfaces to keep in agreement, and s-modal owns the layout inside it.

Fits when

  • Merchants mostly watch, and workers do the marking on the work page.
  • Interventions are rare enough that a click is cheap.

Recommendation

B for the model, A for the chrome, D for Manage

The three fixes are independent and can land in that order. None of them requires the others.

  1. Ship A's chrome first. Delete the “started for N items” line, drop the “Line items” wrapper, move the block reason out of the badge into a wrapping strip, put one Mark-done on the live step and everything else behind ⋯, and make Attach a link. That is a render-only change to one route and it removes most of the noise.
  2. Then adopt B's naming, even without B's layout. “Making” and “Shipping” — or the workflow's own name with “after every item is made” underneath — costs nothing and retires the “workflow card vs order workflow card” confusion the fastest.
  3. Then move Manage into D's drawer if step editing keeps growing. It's the only one of the four that stays calm as interventions accumulate.

C I'd hold back — but keep it in mind for the orders index, where a table of what's blocked across every order is the view a production manager actually opens each morning, and where this page's card model genuinely doesn't scale.

The rule underneath all four: a badge holds a word from a closed set; a strip holds a sentence; a card holds one thing you can name. Applied consistently, the page gets quiet on its own.

Open questions

Five answers that change the design

01 How many line items does a real order carry?

One or two makes A or B right. Five or more makes C right and makes B's Making column awkward. Everything else follows from this.

02 Does the merchant mark steps done here, or only intervene?

If they work the order from this page, the button stays inline (A/B). If workers own the work page and the merchant only unblocks and reopens, D's drawer costs nothing.

03 Is the order workflow always shipping-shaped?

B's “Making → Shipping” is a strong claim. If shops use the order workflow for QA, invoicing or anything post-make, the honest phase label is “After every item is made”.

04 Can an item carry more than one workflow in practice?

The data model allows it; if it's rare, the item card can assume one run and treat a second as the exception — which simplifies every direction above.

05 Should block reasons be long?

Two lines clamped with “Show more” assumes a sentence. If merchants write paragraphs, the reason belongs in a notes thread with a timestamped history, not a field.

Mockups are static HTML at Polaris-like proportions — spacing and tone are indicative, not tokens.
